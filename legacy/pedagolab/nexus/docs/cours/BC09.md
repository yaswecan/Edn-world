## BC09-C1-1 — Déployer une application statique

### FIRST UPLINK // Local n’est pas public

**Typologie et niveau source :** Savoir-faire technique · Non précisé

**Outils source :** LiveServer, GitHub Pages / Netlify

### Situation d’entrée

Le site marche sur localhost, mais personne d’autre ne peut l’ouvrir. Prépare une première mise en ligne autorisée.

### Cours d’introduction proposé

Live Server sert un site de développement local ; ce n’est pas à lui seul une mise en production publique. Un déploiement statique publie HTML, CSS, JavaScript et assets sur un hébergement adapté comme l’espace GitHub Pages ou Netlify autorisé. Le navigateur exécute ensuite le code client, mais ce type d’hébergement n’exécute pas automatiquement du PHP.

Vérifie chemins relatifs, casse des noms, page d’entrée et ressources. Retire secrets et données personnelles avant publication. Teste l’adresse publiée dans une nouvelle session, sur une autre largeur et par les parcours attendus. Conserve la version livrée et un moyen de retour arrière.

### Exemple

```text
localhost → poste local. URL publiée → hébergement choisi. Vérification : HTML, CSS, image et lien interne chargent depuis l’URL réelle.
```

### Production

Déploie la page de TP sur un espace autorisé puis compare local et distant en relevant les chemins.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Adresse publiée autorisée
- version
- parcours testé
- distinction serveur local/hébergement

### Transfert individuel

Le site est publié dans un sous-répertoire et les images sont absentes. Quel problème de chemin recherches-tu ?

### Jeu d’amorce — questions et correction professeur

Live Server ouvert sur ton PC prouve-t-il une publication publique ?

Attendu : Non

L’adresse locale et l’hébergement distant ne désignent pas le même service.

Attendu : Non

Le runtime serveur doit être prévu par l’hébergement.

## BC09-C1-2 — Déployer une application PHP/MySQL

### PHP DEPLOY // Transporter tout le système

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** Hébergement mutualisé (O2switch, Hostinger...) ou VPS

### Situation d’entrée

Les fichiers PHP sont copiés, mais le site ne connaît pas sa base. Prépare code, configuration et données sans envoyer les secrets au dépôt.

### Cours d’introduction proposé

Déployer PHP/MySQL nécessite un runtime compatible, un serveur web, les extensions requises, une base et sa configuration. Le transfert des fichiers n’est qu’une étape : dépendances, variables d’environnement, migrations ou schéma, droits et point d’entrée doivent correspondre au projet.

Prépare une sauvegarde et un retour arrière avant toute modification de l’environnement cible. Ne publie pas fichiers secrets, journaux internes ou répertoires de développement. Teste un parcours complet et inspecte les logs si une erreur survient. L’exercice s’effectue sur l’hébergement de TP approuvé, jamais sur une production existante sans procédure et autorisation.

### Exemple

```text
Checklist : versions → dépendances → configuration locale cible → base et utilisateur → transfert/version → test HTTP → test de persistance → retour arrière.
```

### Production

Déploie le starter sur la cible de TP, configure la base séparément et vérifie création puis lecture après recharge.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Cible autorisée
- configuration sans secret dans le rendu
- parcours réel
- sauvegarde/retour arrière

## BC09-C2-1 — Découverte des fondamentaux du terminal Linux

### SERVER MAZE // Naviguer sans détruire

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** Linux (terminal)

### Situation d’entrée

Sur la VM de déploiement, le site est dans un autre dossier que prévu. Retrouve fichier, droits et trace avant de modifier.

### Cours d’introduction proposé

Les commandes connues du terminal changent de contexte quand elles s’appliquent à un serveur. Pwd, ls, cd, mkdir et grep servent à observer l’arborescence, retrouver une configuration ou lire un journal. Un chemin relatif dépend toujours du dossier courant.

Distingue compte connecté, propriétaire de fichier et utilisateur du service web. Le fait de pouvoir lire un fichier dans ta session ne garantit pas que le service possède le même accès. Préserve le principe de droits nécessaires, évite les permissions universelles et documente les changements. Les manipulations se limitent au répertoire de laboratoire désigné.

### Exemple

```text
pwd
ls -l
grep "ERROR" logs/app.log
# Comparer propriétaire, groupe et droits avec l’utilisateur du service autorisé.
```

### Production

Retrouve le fichier de page et le journal dans la VM, puis explique un défaut de droit fourni sans chmod global.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Chemins
- commandes et résultats
- propriétaire/service distingués
- correction limitée

### Transfert individuel

## BC09-C2-2 — Administration des systèmes Linux

### SERVER SETUP // Préparer sans se verrouiller dehors

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** Linux (terminal), SSH

### Situation d’entrée

La VM doit exécuter PHP, mais une modification SSH mal préparée pourrait couper l’accès. Planifie et vérifie chaque étape.

### Cours d’introduction proposé

Administrer un système pour une application consiste à installer ses dépendances, configurer les services et vérifier leur fonctionnement. Identifie la distribution, le gestionnaire de paquets, les versions et le compte de service. Les commandes du cours doivent être adaptées à la VM réellement utilisée.

Pour modifier SSH, valide la configuration, maintiens un accès de secours et teste une seconde connexion avant de fermer la première. Un changement de port peut réduire du bruit automatisé, mais ne remplace ni clés, ni restrictions, ni mises à jour. Installe uniquement les composants nécessaires au projet et vérifie la chaîne web-runtime-base.

### Exemple

```text
Plan de TP : inventaire → documentation des paquets → installation autorisée → vérification service → configuration SSH testée → second accès → déploiement.
```

### Production

Prépare la VM PHP selon sa documentation et démontre qu’un nouvel accès fonctionne après le changement autorisé.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Versions
- dépendances
- service actif
- accès de secours
- test de deuxième session

### Transfert individuel

### Jeu d’amorce — questions et correction professeur

## BC09-C3-1 — Connexion SSH et transfert de fichiers (Raspberry Pi)

### REMOTE RELAY // Copier vers la bonne machine

**Typologie et niveau source :** Savoir-faire technique · Non précisé

**Outils source :** SSH, Raspberry Pi

### Situation d’entrée

Le fichier est prêt, mais deux terminaux se ressemblent. Identifie local et Raspberry Pi avant le transfert.

### Cours d’introduction proposé

SSH ouvre une session distante sécurisée vers une machine autorisée. Le nom d’utilisateur, l’hôte et éventuellement le port identifient la cible. La clé d’hôte aide à vérifier l’identité du serveur ; une alerte de changement ne doit pas être ignorée automatiquement.

Scp ou SFTP transfèrent des fichiers via SSH selon l’outil et sa version. Avant le transfert, identifie source, destination et droits. Après copie, vérifie présence et contenu sur la cible, par exemple avec une empreinte calculée des deux côtés. Une commande locale et une commande distante peuvent afficher des chemins semblables tout en visant des machines différentes.

### Exemple

```text
Schéma de commande : ssh utilisateur@hote-autorise ; transfert scp fichier utilisateur@hote-autorise:chemin-de-labo/. Les vraies valeurs sont fournies par le professeur.
```

### Production

Connecte-toi au Raspberry Pi ou à la cible de substitution explicitement notée, copie un fichier de TP et vérifie-le.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Cible et identité vérifiées
- distinction local/distant
- copie et intégrité
- matériel utilisé déclaré

### Transfert individuel

## BC09-C3-2 — Connexion SSH en contexte serveur de production

### PRODUCTION LINK // Se connecter avec méthode

**Typologie et niveau source :** Savoir-faire technique · Non précisé

**Outils source :** SSH

### Situation d’entrée

Le serveur de préproduction écoute sur un port non standard. Prépare la connexion sans publier ta clé ni multiplier les essais au hasard.

### Cours d’introduction proposé

Une connexion SSH dépend de l’utilisateur, de l’hôte, du port, de l’identité du serveur et du moyen d’authentification. Le contexte de production ajoute des contraintes d’autorisation, de traçabilité et de disponibilité. L’exercice se déroule ici sur une préproduction de TP.

Vérifie la cible fournie et le périmètre, protège la clé privée, utilise une configuration explicite et commence par des observations non destructives. Un refus de connexion, un délai expiré et un refus d’authentification n’indiquent pas la même étape. Le port modifié ne garantit aucune sécurité à lui seul. Termine la session et consigne les opérations utiles sans exposer de secrets.

### Exemple

```text
ssh -p PORT utilisateur@hote-autorise
# PORT est remplacé par la valeur communiquée, sans scanner d’autres machines.
```

### Production

Établis l’accès de TP sur le port donné, identifie la machine et produis un journal d’intervention expurgé.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Connexion réelle autorisée
- cible vérifiée
- message d’erreur catégorisé
- clé non partagée

## BC09-C4-1 — Sécurisation basique d'un serveur

### BASTION RULES // Défendre sans bloquer la classe

**Typologie et niveau source :** Savoir-faire technique · Non précisé

**Outils source :** SSH / pare-feu basique

### Situation d’entrée

Une règle de pare-feu menace l’accès administrateur autorisé. Choisis une protection minimale et testable avec retour arrière.

### Cours d’introduction proposé

Le durcissement combine plusieurs mesures : mises à jour, comptes limités, accès SSH adaptés, pare-feu et observation. Le pare-feu contrôle des flux selon ses règles ; il n’est pas un antivirus ni une preuve d’authentification. Les clés SSH réduisent certains risques liés aux mots de passe lorsqu’elles sont correctement protégées.

Fail2ban peut réagir à des événements de journaux selon ses filtres et actions ; son installation seule ne prouve pas son efficacité. Un honeypot sert à observer une activité dans un périmètre contrôlé et ne protège pas automatiquement les services réels. Avant toute restriction, conserver un accès de secours et vérifier les flux légitimes. Les exercices utilisent une VM isolée et des événements fictifs.

### Exemple

```text
Matrice de TP : SSH administrateur autorisé ; service web prévu ; autres entrées non nécessaires refusées. Tests avant/après et procédure de récupération.
```

### Production

Applique les règles autorisées sur la VM, vérifie un flux permis et un flux interdit, puis démontre une réaction fail2ban sur logs de TP.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Règles documentées
- accès légitime conservé
- refus vérifié
- retour arrière
- limites du port et du honeypot

### Transfert individuel

Un ban bloque un utilisateur légitime. Quels journaux et paramètres relis-tu avant de désactiver toute la protection ?

### Jeu d’amorce — questions et correction professeur

Le pare-feu doit être testé…

Attendu : Sur les flux autorisés et interdits

Une protection utile conserve le service attendu.

Un honeypot doit-il être déployé sans accord sur le réseau de l’école ?

Attendu : Non, seulement dans le périmètre isolé autorisé

L’observation et les risques doivent rester maîtrisés.

Notions de base : pare-feu, accès SSH sécurisé (clé vs mot de passe)

## BC09-C5-1 — Lire des logs serveur et corriger des erreurs de production

### LOG BLACKBOX // Lire avant de redémarrer

**Typologie et niveau source :** Savoir-faire technique · Non précisé

**Outils source :** Logs serveur (cPanel / SSH)

### Situation d’entrée

Le portail alterne 404 et 500. Les journaux fictifs contiennent la cause ; ne redémarre pas tout avant de l’avoir cherchée.

### Cours d’introduction proposé

Les logs enregistrent des événements utiles au diagnostic : date, composant, requête, niveau et message selon la configuration. Un statut 200 indique une réussite HTTP pour la demande traitée ; 404 une ressource non trouvée ; 500 une erreur interne. Ces codes ne décrivent pas à eux seuls la cause exacte ni la qualité du rendu.

Reproduis le problème, note l’heure et retrouve les lignes correspondantes. Formule une hypothèse, isole la cause et vérifie une correction limitée. Compare logs applicatifs et serveur si nécessaire. Ne diffuse pas de secrets, tokens ou données personnelles contenus dans un journal. Une remise doit être expurgée et conserver uniquement les traces utiles.

### Exemple

```text
12:01 GET /ancien-chemin 404
12:02 POST /alertes 500 request_id=lab-7
12:02 app request_id=lab-7 connexion base refusée
Ces lignes sont fictives et servent au raisonnement.
```

### Production

Relie les traces, classe les erreurs puis reproduis et corrige un incident sur le projet de TP.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Journal avant/après expurgé
- identifiant de corrélation
- hypothèse
- correction vérifiée

### Transfert individuel

La page répond 200 mais son contenu est incorrect. Quels journaux ou tests applicatifs complètent le statut ?

### Jeu d’amorce — questions et correction professeur

Un 500 prouve-t-il que le DNS ne résout pas ?

Attendu : Non, une réponse serveur a été reçue

Il faut distinguer la couche atteinte et la cause applicative.

Que faire des tokens présents dans un log à partager ?

Attendu : Les retirer ou masquer avant diffusion

Le diagnostic doit minimiser les données sensibles.
