## BC07-C1-1 — Langage serveur - syntaxe et structures de base PHP

### PHP REACTOR // Le calcul côté serveur

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** PHP natif

### Situation d’entrée

Le serveur calcule mal les réserves et affiche ses variables au lieu du résultat. Passe du raisonnement connu à la syntaxe PHP.

### Cours d’introduction proposé

PHP s’exécute côté serveur ou en ligne de commande. Ses variables commencent par $, les conditions et boucles organisent les traitements, les fonctions reçoivent des paramètres et renvoient des résultats. Les tableaux peuvent associer des index ou des clés. Le HTML reçu par le navigateur n’est pas le fichier PHP source.

Une fonction récursive s’appelle elle-même pour un sous-problème plus simple. Elle nécessite un cas d’arrêt et une progression vers ce cas ; la récursion n’est pas une optimisation automatique. Sépare calcul et affichage, écris un contrat et teste plusieurs valeurs. Les messages d’erreur PHP se lisent dans le terminal ou les journaux du laboratoire.

### Exemple

```text
<?php
function total(array $valeurs): int {
  $somme = 0;
  foreach ($valeurs as $v) { $somme += $v; }
  return $somme;
}
echo total([2, 3]);
```

### Production

Exécute le starter PHP local, corrige un calcul avec boucle, ajoute une fonction puis une petite récursion bornée.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Script PHP réellement exécuté
- résultats de tests
- paramètres/retour
- cas d’arrêt de la récursion

## BC07-C1-2 — Langage serveur - transmission de données et gestion d'état HTTP

### STATE TOKEN // HTTP n’a pas de mémoire magique

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** PHP natif

### Situation d’entrée

La page oublie le secteur choisi et confond une donnée GET avec une preuve d’identité. Distingue données, cookies et session.

### Cours d’introduction proposé

HTTP transporte des requêtes et des réponses ; l’état d’une application doit être organisé explicitement. GET transmet des paramètres dans l’URL ; POST peut transmettre des données dans le corps. En PHP, les tableaux superglobaux donnent accès à ces informations selon leur mode d’envoi. Un cookie est stocké côté client puis envoyé selon ses règles ; une session associe un identifiant à un état géré côté serveur.

Ne considère pas un champ reçu ou un cookie de rôle comme une autorisation fiable. Pour les dates, précise format et fuseau au lieu de comparer des chaînes arbitraires. Choisis des réglages de cookie adaptés, n’inscris pas de secrets dans les URL et teste une nouvelle session ainsi que la déconnexion.

### Exemple

```text
Requête de filtre : GET /alertes?secteur=nord. Envoi de formulaire : POST /signalements. Session : identité issue d’une authentification vérifiée, pas de ?role=admin.
```

### Production

Dans le TP PHP, reçois GET et POST, conserve une préférence de session et affiche une date avec fuseau explicite.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Échanges observés
- distinction cookie/session
- date expliquée
- données client non utilisées comme droit

### Transfert individuel

Deux onglets utilisent la même session. Que doit-il se passer après la déconnexion de l’un ?

### Jeu d’amorce — questions et correction professeur

Un paramètre role=admin suffit-il à authentifier ?

Attendu : Non

GET ou POST ne rend pas fiable une donnée déclarée par le client.

Une session PHP implique…

Attendu : Un état serveur associé à un identifiant

L’état applicatif est distinct de la connexion réseau.

## BC07-C1-3 — Coder dans un langage orienté objet (Programmation Orientée Objet)

### CLASS FACTORY // Des objets responsables

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** PHP natif (POO)

### Situation d’entrée

Les drones partagent identifiant et énergie, mais un modèle de secours possède une capacité spécifique. Modélise sans copier tout le code.

### Cours d’introduction proposé

La programmation orientée objet regroupe état et comportements dans des classes. Un objet est une instance ; propriétés et méthodes portent ses données et actions. Le constructeur initialise un état cohérent ; la visibilité limite les accès directs. L’héritage permet une spécialisation, à utiliser lorsqu’une relation « est un » a du sens.

Créer une classe et un héritage n’est pas seulement ajouter des mots-clés. Vérifie que les objets respectent leurs invariants et peuvent être utilisés sans connaissance de détails internes. Évite de tout rendre public ou de fabriquer des hiérarchies inutiles. La composition est une autre option à comparer lorsque l’objet « possède » un service plutôt qu’il « est » un type spécialisé.

### Exemple

```text
<?php
class Drone { public function role(): string { return "surveillance"; } }
class DroneSecours extends Drone { public function role(): string { return "secours"; } }
echo (new DroneSecours())->role();
```

### Production

Crée une classe PHP avec état et méthode, une classe dérivée et deux instances ; teste un invariant d’énergie.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Classe et héritage réellement exécutés
- instances distinctes
- invariant et choix d’héritage justifiés

### Transfert individuel

Un drone possède un journal d’événements. Faut-il que Drone hérite de Journal ?

### Jeu d’amorce — questions et correction professeur

Une instance et une classe sont…

Attendu : Un objet concret et sa définition

Plusieurs objets peuvent être créés à partir d’une classe.

« Drone possède Journal » suggère d’abord…

Attendu : Une composition plutôt qu’un héritage automatique

Le type de relation doit guider la structure.

Classes, objets, héritage de base

## BC07-C2-1 — Structurer un backend en architecture MVC

### MVC SECTOR // Chaque fichier sa mission

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** PHP natif (MVC simplifié)

### Situation d’entrée

Un seul fichier reçoit la requête, exécute du SQL, décide des droits et dessine l’écran. Sépare les responsabilités pour pouvoir corriger sans tout casser.

### Cours d’introduction proposé

MVC distingue modèle, vue et contrôleur. Le contrôleur organise le traitement d’une requête ; le modèle porte les données et la logique appropriée à l’application ; la vue représente le résultat. Un routeur oriente la requête vers le bon traitement. Une architecture simplifiée peut suffire pour apprendre, à condition de rendre les flux lisibles.

Le but n’est pas de multiplier les dossiers vides. Les responsabilités doivent être vérifiables : pas de SQL dans la vue, pas de HTML dispersé dans les accès aux données. Le front controller centralise l’entrée ; les erreurs reçoivent un traitement cohérent. Teste un parcours de bout en bout et explique où une règle serait modifiée.

### Exemple

```text
public/index.php → route → AlertController → AlertRepository → vue. L’emplacement de la règle métier est documenté ; les noms de dossiers seuls ne prouvent pas MVC.
```

### Production

Réorganise le starter PHP en routes, contrôleur, modèle et vue ; dessine la circulation d’une requête.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Fichiers réels
- responsabilités distinctes
- parcours testé
- schéma conforme au code

### Transfert individuel

### Jeu d’amorce — questions et correction professeur

La séparation permet de tester et faire évoluer indépendamment.

## BC07-C2-2 — Concevoir et exposer une API REST

### REST FORGE // Une API qui tient son contrat

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** PHP natif, REST

### Situation d’entrée

La route renvoie 200 même pour une ressource absente et accepte une énergie négative. Construis une API qui exprime réellement son résultat.

### Cours d’introduction proposé

Une API REST expose des ressources et utilise les méthodes HTTP selon leur sens. GET lit sans modification intentionnelle ; POST crée ou déclenche selon le contrat ; PUT remplace une représentation ; DELETE demande une suppression. Les routes identifient la ressource, le contrôleur valide et traite, la réponse porte statut, en-têtes et données.

Le routage manuel peut passer par un front controller PHP. Renvoie du JSON avec un type de contenu cohérent. Distingue demande invalide, accès non autorisé, absence et erreur interne ; n’expose pas les détails sensibles des exceptions. Les règles métier doivent être vérifiées avant persistance. La connexion PDO et les paramètres préparés gardent données et instructions SQL séparées.

### Exemple

```text
GET /alertes/42 → 200 + alerte si présente ; 404 si absente. POST /alertes avec données invalides → erreur documentée, sans insertion.
```

### Production

Crée lecture et création dans le TP PHP, puis étends à PUT/DELETE et documente les réponses et la validation.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Routes exécutées
- statuts cohérents
- JSON valide
- règle métier
- requête PDO préparée si persistance activée

### Transfert individuel

Une création valide échoue à cause de la base. Comment réponds-tu sans annoncer un succès ni divulguer le secret de connexion ?

### Jeu d’amorce — questions et correction professeur

Attendu : Un statut d’absence adapté, par exemple 404

Le statut fait partie du contrat de réponse.

Valider l’énergie doit se faire…

Attendu : Avant de persister une valeur contraire à la règle

La logique serveur protège la cohérence des données.

## BC07-C2-4 — Comprendre une architecture 3-tiers et consommer une API

### THREE TIERS // Suivre une donnée

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** Fetch / Ajax

Le navigateur veut écrire directement en base. Reconstitue présentation, logique et persistance, puis raccorde un appel asynchrone.

### Cours d’introduction proposé

L’architecture trois tiers distingue présentation, logique applicative et données. Ces responsabilités peuvent être déployées de plusieurs façons : trois tiers ne signifie pas toujours exactement trois machines. Le frontend collecte et présente ; le backend contrôle et traite ; la base assure la persistance selon son modèle.

Le flux entrée → validation → traitement → persistance → restitution aide à situer une erreur. Les appels asynchrones doivent gérer attente, échec et résultat cohérent. Une modification du DOM n’est pas une écriture persistée ; une réponse positive ne doit pas être émise avant le résultat réel du traitement prévu.

### Exemple

```text
Formulaire → fetch → route PHP → validation → PDO → base → JSON → mise à jour DOM.
```

## BC07-C3-1 — Comprendre les attaques courantes

### THREAT MAP // Comprendre pour protéger

**Typologie et niveau source :** Savoir · A2

**Outils source :** OWASP Top 10

### Situation d’entrée

Trois incidents fictifs touchent affichage, requête SQL et action de session. Associe chaque risque à une défense au bon endroit.

### Cours d’introduction proposé

Une XSS exploite l’interprétation de contenu comme code dans le navigateur ; la protection dépend notamment du contexte de sortie et de l’usage d’API sûres. Une injection SQL mélange données et instructions ; des requêtes préparées paramétrées évitent ce mélange pour les valeurs. Une CSRF vise à faire réaliser une action par un navigateur disposant déjà d’un contexte d’authentification.

Valider une entrée, encoder une sortie et autoriser une action sont trois fonctions différentes. Aucun filtre universel ne règle tous les contextes. Les démonstrations restent sur l’application fictive, avec données et comptes de laboratoire, puis se terminent par une correction et des tests. La classification OWASP sert de repère, pas de liste exhaustive de toutes les failles.

### Exemple

```text
Texte externe affiché → textContent ou encodage adapté. Valeur dans SQL → paramètre PDO. Action de session → contrôle anti-CSRF et autorisation adaptés.
```

## BC07-C3-2 — Sécuriser un formulaire et valider les entrées

**Typologie et niveau source :** Savoir-faire technique · A2

Validation signifie accepter ou refuser selon des règles ; normalisation transforme une représentation convenue ; encodage protège un contexte de sortie. Ces opérations ne sont pas interchangeables. Prévois les cas limites, champs absents, valeurs vides et erreurs lisibles. Ne « nettoie » pas silencieusement une donnée jusqu’à en changer le sens. Le traitement et la persistance n’avancent qu’après validation pertinente.

### Exemple

```text
$email = filter_var($entree["email"] ?? "", FILTER_VALIDATE_EMAIL);
// Puis vérifier les règles métier et répondre sans divulguer de données sensibles.
```

## BC07-C3-3 — Authentifier un utilisateur de manière sécurisée

### SESSION GUARD // Identité et permission

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** PHP (session, password_hash) / CTF

### Situation d’entrée

Un compte de test connecté tente de lire le dossier d’un autre. L’authentification marche ; l’autorisation manque.

### Cours d’introduction proposé

Authentifier consiste à vérifier une identité ; autoriser consiste à décider si cette identité peut effectuer une opération sur une ressource. En PHP, password_hash produit un hachage adapté au mot de passe et password_verify vérifie une tentative. Le hachage n’est pas un chiffrement réversible destiné à récupérer le secret.

La session doit être configurée, renouvelée lors d’un changement pertinent d’authentification et détruite à la déconnexion. Vérifie les droits sur chaque ressource, limite les tentatives et évite les messages qui exposent inutilement l’existence d’un compte. Le durcissement SSH, pare-feu et fail2ban relève aussi des ateliers système du référentiel, et ne se démontre pas avec un login PHP seul.

### Exemple

```text
Compte A connecté + dossier appartenant à B → refus si aucun droit de partage. Mot de passe de TP uniquement, jamais une valeur personnelle dans le dépôt.
```

### Production

Dans le TP autorisé, implémente hash/vérification, session et contrôle de propriétaire ; réalise les cas anonyme, propriétaire et autre compte.

Mode : TP réel dans l’outil indiqué, hors sandbox

## BC07-C4-1 — Tester des routes API avec Postman

### POSTMAN PROBE // Le contrat sous test

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** Postman

### Situation d’entrée

Une route répond, mais avec le mauvais statut et un champ absent. Lance des requêtes qui vérifient davantage que « le serveur est vivant ».

## BC07-C4-2 — Exécuter des tests unitaires fournis

### TEST RIG // Faire parler les tests fournis

### Situation d’entrée

### Cours d’introduction proposé

Un test compare un comportement obtenu à un résultat attendu. Un test unitaire cible une unité de comportement ; un test d’intégration vérifie une coopération ; un test de charge observe un système sous une sollicitation définie. La recette fonctionnelle vérifie le besoin du point de vue de l’usage.

L’élève exécute ici des tests fournis. Lis le nom du cas, les données, l’assertion et le message d’échec. Reproduis puis corrige le code, avant de relancer la suite complète. Ne modifie un test que si son contrat a été explicitement arbitré. Un test vert n’est pas une preuve d’absence de toute erreur ; documente sa portée.

### Exemple

```text
Test fourni : énergieRestante(3, 5) doit retourner 0, pas -2. Correction dans la logique métier, puis relance de tous les cas.
```

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** Laravel (initiation A2)

### Situation d’entrée

Un dépôt Laravel paraît inconnu. Ne copie pas des commandes au hasard : repère version, prérequis, routes et templates.

### Cours d’introduction proposé

Un framework propose une structure et des outils pour des besoins récurrents. Laravel organise notamment routage, contrôleurs, vues Blade et accès aux données avec un ORM. Composer gère les dépendances PHP ; les commandes du projet doivent correspondre à sa version et à ses prérequis.

Commence par le README, composer.json et la documentation de la version choisie. Prépare l’environnement de laboratoire, installe sans exposer de secrets, lance un parcours minimal puis situe chaque fichier. Compare l’intérêt du framework au PHP natif : conventions et services disponibles contre apprentissage de l’écosystème, dépendances et contraintes. Un ORM ne supprime ni SQL, ni les règles de validation, ni l’autorisation.
