## BC02-C1-1 — Installer un système d'exploitation (OS)

### BOOT SECTOR // Installer sans détruire

**Typologie et niveau source :** Savoir-faire technique · A1/A2

**Outils source :** Linux (dualboot) A1 
Windows A2

### Situation d’entrée

Le poste de formation ne possède pas l’OS demandé. Deux boutons proposent « effacer le disque » et « créer une VM ». Prépare une installation réversible.

### Cours d’introduction proposé

Un système d’exploitation gère le matériel, les fichiers, les processus et les accès. Installer un OS demande de vérifier l’image, l’architecture compatible, les ressources et le disque cible. Une machine virtuelle utilise un matériel virtualisé à l’intérieur d’un OS hôte. Un dualboot installe plusieurs OS démarrables sur la machine ; ce n’est pas une VM. Cette distinction est une précision pédagogique, le texte source mentionnant les deux ensemble.

Pour une première manipulation, utilise la VM autorisée par le professeur, un disque virtuel neuf et des données fictives. Prépare sauvegarde ou instantané, décris les choix, termine l’installation, redémarre puis vérifie l’OS et le réseau. Une capture de l’assistant d’installation ne suffit pas : il faut démontrer un système utilisable.

### Exemple

```text
Plan : vérifier image et ressources → créer la VM → identifier son disque virtuel → installer → redémarrer → vérifier version, compte et réseau.
```

### Production

Planifie l’opération dans le jeu puis installe réellement l’OS dans la VM préparée par le professeur.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- VM démarrée
- disque cible identifié
- compte de test et version vérifiés
- procédure de retour arrière

### Transfert individuel

Sur une machine contenant déjà des documents, que faut-il vérifier avant une installation en dualboot ?

### Jeu d’amorce — questions et correction professeur

Premier exercice sur un PC contenant des données ?

Attendu : Utiliser la VM et le disque virtuel autorisés

Le laboratoire doit être réversible et ne pas toucher aux données du poste.

Une VM et un dualboot sont-ils identiques ?

Attendu : Non : OS invité virtualisé contre choix au démarrage

Le choix d’environnement change le risque, les ressources et la procédure.

## BC02-C1-2 — Installer et configurer des outils de développement

### DEV RIG // Le poste qui ne formate plus

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** VS Code

### Situation d’entrée

Le fichier s’ouvre, mais le formatage ne marche pas et le débogueur ne s’arrête jamais. Configure seulement les outils nécessaires à cette mission.

### Cours d’introduction proposé

Un environnement de développement associe éditeur, navigateur, runtime, extensions et réglages de projet. L’IDE aide à lire, écrire, formater et déboguer ; il n’est pas le runtime. Une extension peut ajouter une fonction mais aussi des dépendances ou des accès. Vérifie son éditeur, son utilité et la politique de l’établissement.

Teste chaque configuration avec un petit fichier : ouverture du projet, coloration, formatage, exécution et arrêt sur un point d’arrêt. Si une fonction échoue, lis le message et vérifie le langage reconnu, l’outil sélectionné et son installation. Distingue réglage utilisateur et réglage partagé du projet. Un poste « prêt » est un poste dont le cycle code-exécution-débogage a été démontré.

### Exemple

```text
Fichier test : const message = "NEXUS"; console.log(message); Le professeur fournit un projet et le formatage attendu.
```

### Production

Choisis les outils puis démontre dans VS Code ouverture, formatage et un point d’arrêt sur le projet local.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Liste minimale justifiée
- réglage de projet
- observation d’une variable pendant un arrêt du débogueur

### Transfert individuel

### Jeu d’amorce — questions et correction professeur

## BC02-C2-1 — Utiliser un gestionnaire de versionning

### TIME VAULT // Sauver un état utile

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** Git / GitHub

### Situation d’entrée

Le portail fonctionnait hier. Tu as trois copies nommées final-vrai-final. Crée un historique que ton futur binôme peut comprendre.

### Cours d’introduction proposé

Git conserve un historique de versions d’un projet. Le répertoire de travail contient les fichiers modifiés ; l’index sélectionne ce qui entrera dans le prochain commit ; le commit enregistre un état avec un message. GitHub est un service d’hébergement et de collaboration autour de dépôts, pas un autre nom de Git.

Commence par lire git status et git diff. Sélectionne des changements cohérents, vérifie qu’aucun secret n’est inclus, puis crée un commit explicite. Cloner récupère un dépôt ; pousser publie des commits vers un dépôt distant autorisé ; récupérer ou intégrer les changements permet de se synchroniser. Un commit local n’est pas encore une copie distante, et Git ne remplace pas toute stratégie de sauvegarde.

### Exemple

```text
git status
git diff
git add README.md
git commit -m "Documenter le lancement du portail"
git log --oneline
```

### Production

Crée un dépôt de laboratoire, deux commits cohérents et retrouve la version antérieure d’un fichier sans perdre le travail actuel.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Historique réel
- messages explicites
- diff relu
- distinction commit local et push expliquée

### Transfert individuel

Un fichier de secret est visible dans le diff avant commit. Comment interromps-tu proprement la publication ?

### Jeu d’amorce — questions et correction professeur

Que vérifie-t-on avant git add ?

Attendu : Le contenu du diff et les fichiers sensibles

Le versionnement publie aussi les erreurs : lire le diff fait partie du travail.

Un commit existe localement. Est-il déjà sur GitHub ?

Attendu : Pas sans transfert vers le dépôt distant

Git et le service distant ont des états distincts.

## BC02-C2-2 — Utiliser un gestionnaire de versionning en contexte collaboratif

### MERGE COLLISION // Deux branches, une porte

**Typologie et niveau source :** Savoir-faire technique · Non précisé

**Outils source :** Git / GitHub

### Situation d’entrée

Deux agents ont changé le même message d’accès. Git refuse de décider à votre place : reconstruisez la version correcte, sans supprimer le travail du binôme.

### Cours d’introduction proposé

Une branche permet de faire évoluer une ligne de travail. Une fusion combine des historiques ; un conflit apparaît lorsque Git ne peut pas décider automatiquement entre des modifications. Les marqueurs de conflit délimitent des versions à examiner, pas du code à conserver.

Lis l’intention des deux changements, échange avec l’auteur et construis une résolution qui respecte le besoin. Exécute les tests, vérifie le diff final et termine la fusion. Une Pull Request rend la proposition visible avant intégration : contexte, changements, vérification et commentaires y servent à collaborer. Forcer une publication pour faire disparaître le problème n’est pas une méthode de résolution. La trace attendue montre aussi le raisonnement et la coopération.

### Exemple

```text
Version A : message précis. Version B : association accessible label/champ. Résolution attendue : garder la précision ET l’association, puis tester.
```

### Production

Dans un dépôt jetable, crée deux branches en binôme, provoque le conflit prévu et fusionne après relecture croisée.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Branches et fusion réelles
- conflit expliqué
- tests après résolution
- commentaire de PR constructif

### Transfert individuel

La fusion est sans conflit Git mais le comportement devient incorrect. Que faut-il ajouter à la vérification ?

### Jeu d’amorce — questions et correction professeur

Git demande une résolution. Premier geste ?

Attendu : Lire les deux intentions et le contexte

Une résolution sémantique protège les deux besoins, pas seulement la syntaxe.

Fusion sans conflit signifie…

Attendu : Que Git a pu fusionner, pas que les tests passent

La cohérence fonctionnelle ne se déduit pas de la seule fusion.

### Notions du socle (texte source, ligne 38)

> Branches / Merge / résolution de conflits simples
> Pull Request, commentaires

## BC02-C3-1 — Utiliser les commandes Linux

### SHELL MAZE // Retrouver la trace

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** Linux (terminal)

### Situation d’entrée

Le journal de NEXUS est caché dans une arborescence de laboratoire. Retrouve ERROR sans modifier les fichiers du système.

### Cours d’introduction proposé

Un terminal permet d’interagir avec un shell. pwd montre le répertoire courant ; ls liste ; cd change de répertoire ; mkdir crée un dossier ; grep recherche du texte. Un chemin absolu part de la racine, un chemin relatif dépend du dossier courant. Créer, lire et éditer un fichier sont des actions distinctes.

Les permissions déterminent qui peut lire, écrire ou exécuter. Un compte ordinaire limite les conséquences d’une erreur ; les droits administrateur ne doivent servir qu’à une tâche autorisée. Les gestionnaires de paquets diffèrent selon l’OS. Identifier la distribution précède le choix d’une commande d’installation. Les manipulations de comptes, paquets et droits se font ici dans une VM jetable, pas sur le serveur qui héberge les travaux des élèves.

### Exemple

```text
pwd
ls
cd labo
mkdir rapports
grep "ERROR" logs/app.log
# Les commandes paquets/comptes sont choisies après identification de la VM.
```

### Production

Dans l’atelier préparé, trouve une erreur, crée un rapport, explique ses droits puis réalise l’exercice de compte et de paquet sur la VM.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Chemin exact

- fichier créé
- droits expliqués
- observation locale des tâches administrateur autorisées
