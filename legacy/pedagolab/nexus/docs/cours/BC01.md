## BC01-C1-1 — Connaître les grandes étapes de l'histoire de l'informatique

### ARCHIVES // Le futur a une histoire

**Typologie et niveau source :** Savoir · Non précisé

**Outils source :** Non précisés

### Situation d’entrée

Le musée de NEXUS a mélangé ses archives. Les machines à cartes perforées portent des étiquettes « cloud » : répare la chronologie avant l’ouverture.

### Cours d’introduction proposé

L’informatique ne commence pas avec le Web. Des machines mécaniques ont précédé les calculateurs électroniques. Le transistor puis les circuits intégrés ont permis de réduire et de multiplier les composants. Les microprocesseurs ont favorisé les ordinateurs personnels ; les réseaux ont permis de relier les machines. Le Web est un service construit sur Internet, pas un synonyme de ce réseau.

Une chronologie utile relie une innovation à un besoin et à une conséquence : calculer, stocker, miniaturiser, échanger. Le cloud ne supprime pas les ordinateurs : il propose des ressources exploitées à distance. Le CPU exécute les instructions ; RAM, stockage et GPU ont des rôles différents. Pour expliquer une technologie actuelle, cherche les contraintes auxquelles elle répond plutôt qu’un inventeur unique de « toute l’informatique ».

### Exemple

```text
Cartes d’archives : calcul mécanique → calculateurs électroniques → transistor → microprocesseur → Web. Pour chaque carte : une contrainte, un changement et une source historique.
```

## BC01-C1-2 — Identifier les composants matériels d'un ordinateur et expliquer leur impact sur les performances d'une application

### CORE REPAIR // Quel composant sature ?

**Typologie et niveau source :** Savoir · Non précisé

**Outils source :** Non précisés

### Situation d’entrée

Le poste de défense ralentit : RAM presque pleine, stockage sollicité et CPU peu occupé. Choisis une hypothèse sans acheter le composant le plus cher.

### Cours d’introduction proposé

Le processeur exécute des instructions. La RAM conserve temporairement les données des programmes en cours ; son contenu n’est pas un stockage durable. Un SSD ou un HDD garde les fichiers après extinction. Le GPU réalise des traitements graphiques et d’autres calculs fortement parallélisables.

Une application est limitée par son goulot d’étranglement : la ressource qui bloque actuellement le travail. Une RAM saturée peut provoquer des échanges plus fréquents avec le stockage. Un GPU plus puissant n’accélère pas toutes les tâches ; un réseau lent ne se répare pas en augmentant automatiquement la RAM. Observe plusieurs indicateurs pendant une action précise, formule une hypothèse et compare après une modification contrôlée.

### Exemple

```text
Mesure fictive : CPU 18 %, RAM 96 %, disque très actif pendant un changement d’onglet. Cette corrélation suggère une pression mémoire ; elle ne prouve pas seule la cause.
```

Mode : Production et observation humaine

### Critères proposés

- Tableau CPU/GPU/RAM/stockage
- relevé avant/après
- hypothèse distinguée d’une preuve

### Transfert individuel

La même page est rapide hors ligne mais lente quand elle charge des données. Quelle autre ressource faut-il examiner ?

### Jeu d’amorce — questions et correction professeur

Premier test raisonnable sur ce poste ?

Attendu : Fermer une application et comparer mémoire et réactivité

Change un facteur et observe : le symptôme seul ne constitue pas un diagnostic.

Que conserve un SSD après extinction ?

Attendu : Les fichiers enregistrés

Sauvegarder un fichier et garder un programme ouvert ne sont pas la même chose.

## BC01-C2-1 — Décrire le cycle complet d'une requête web et distinguer les rôles de chaque composant

### TRACE 2 // La requête perdue

**Typologie et niveau source :** Savoir · Non précisé

**Outils source :** DevTools

### Situation d’entrée

L’adresse nexus.test est saisie, mais aucun tableau de bord ne s’affiche. Reconstitue la chaîne puis place la panne au bon endroit.

### Cours d’introduction proposé

Le navigateur interprète une URL. Si nécessaire, une résolution DNS associe son nom à une adresse. Une connexion permet ensuite l’échange HTTP ; avec HTTPS, TLS protège le transport. Le serveur reçoit une requête, applique un traitement et renvoie une réponse comprenant un statut, des en-têtes et éventuellement un corps. Le navigateur interprète les ressources et construit le rendu. D’autres requêtes peuvent être nécessaires pour CSS, JavaScript, images ou données.

Le nom de domaine n’est pas l’hébergement. Un serveur désigne ici un rôle logiciel, souvent installé sur une machine adaptée à un service continu. Les caches peuvent éviter certaines étapes ; la chaîne proposée est donc une représentation simplifiée. Dans DevTools, distingue panne de résolution, refus de connexion, réponse HTTP et erreur de rendu.

### Exemple

```text
GET /status → HTTP 200 + {"state":"ready"}. Une réponse reçue n’implique pas que le JavaScript qui l’affiche fonctionne.
```

### Production

Ordonne le trajet puis relève dans l’onglet Réseau une URL, une méthode, un statut et le type de réponse d’une page de laboratoire.

Mode : Production et observation humaine

### Critères proposés

- Chaîne annotée
- capture ou relevé DevTools expurgé
- explication de la différence réponse/rendu

### Transfert individuel

Une page renvoie 200 mais reste blanche. Quelles observations distinguent une panne réseau d’une erreur JavaScript ?

### Jeu d’amorce — questions et correction professeur

DNS fonctionne mais le serveur répond 404. La panne est-elle DNS ?

Attendu : Non : une réponse HTTP a été reçue

Le statut appartient à la réponse HTTP, après la résolution nécessaire à cette connexion.

HTTPS protège principalement quoi ?

Attendu : Le transport entre les points de terminaison TLS

HTTPS ne garantit ni l’honnêteté du site ni l’absence de bugs applicatifs.

### Notions du socle (texte source, ligne 15)

> Le fonctionnement du web
> La différence entre un ordinateur de bureau et un serveur informatique
> HTTP, DNS
> cycle complet d'une requête (requête → serveur → réponse → rendu navigateur)

- Connaître le cycle d'une requête HTTP/HTTPS
- Comprendre les notions d’hébergement, domaine, DNS, HTTPS

## BC01-C2-2 — Schématiser l'architecture d'une application web en identifiant les rôles et interactions entre navigateur, serveur et API

### MAP THE CITY // Qui fait quoi ?

**Typologie et niveau source :** Savoir · Non précisé

**Outils source :** Schémas d'architecture

### Situation d’entrée

Un architecte a dessiné le navigateur directement relié à la base avec un mot de passe public. Réattribue les responsabilités avant de reconstruire le schéma.

### Cours d’introduction proposé

Une architecture décrit des responsabilités et leurs interactions. Le navigateur présente une interface et déclenche des demandes. Le serveur applique les règles de l’application. Une API décrit une interface d’échange ; elle n’est pas obligatoirement une machine séparée. La base conserve les données structurées.

Un schéma utile montre le sens de la requête et celui de la réponse, les données qui circulent et les frontières de confiance. Évite les boîtes qui ne disent pas ce qu’elles font. Sur une application classique, les identifiants de la base restent côté serveur. Le développeur doit savoir où un contrôle doit s’exécuter : masquer un bouton dans le navigateur ne suffit pas à autoriser ou interdire une opération serveur.

### Exemple

```text
Navigateur -- requête JSON --> API du serveur -- requête préparée --> base. Réponses dans le sens inverse. API et logique serveur peuvent partager le même processus.
```

### Production

Attribue les rôles, dessine deux flux et place une validation de droit au bon endroit.

Mode : Production et observation humaine

### Critères proposés

- Schéma légendé
- flèches aller/retour
- distinction rôle logique et machine physique

### Transfert individuel

Le serveur rend directement le HTML sans API JSON séparée. L’application a-t-elle cessé d’être une application web ?

### Jeu d’amorce — questions et correction professeur

Où décider si un utilisateur peut supprimer une donnée ?

Attendu : Dans le traitement serveur de cette opération

Le contrôle doit être appliqué sur le composant qui protège réellement les données.

Une API nécessite-t-elle un second ordinateur ?

Attendu : Non, elle peut être exposée par le même serveur

Interface logicielle et équipement physique sont deux descriptions distinctes.

### Notions du socle (texte source, ligne 16)

> Les rôles et interactions : serveur, navigateur, API
> Comprendre le rôle d'une API dans une architecture web

## BC01-C2-3 — Distinguer les principaux protocoles d'échange

### PROTOCOL GATE // Choisir le bon canal

**Typologie et niveau source :** Savoir · Non précisé

**Outils source :** Non précisés

### Situation d’entrée

Trois canaux attendent tes ordres : consulter un tableau, administrer une machine et transférer un fichier. Une carte piège présente « LAN » comme un protocole.

### Cours d’introduction proposé

Un protocole définit des règles d’échange. HTTP sert notamment au Web ; HTTPS ajoute un transport protégé par TLS. SSH fournit un canal d’administration distant protégé. FTP transfère des fichiers mais sa forme classique ne chiffre pas les échanges. SFTP est un protocole de transfert utilisant SSH et ne doit pas être confondu avec FTP.

LAN et WAN décrivent des périmètres de réseau ; VPN désigne une connexion privée virtuelle pouvant s’appuyer sur différents protocoles. Cette précision pédagogique complète la formulation source, qui les regroupe dans les notions réseau. Le choix d’un canal dépend de l’opération, des données, des accès autorisés et des garanties nécessaires. Un tunnel ou HTTPS ne dispense pas de vérifier l’identité et les permissions.

### Exemple

```text
Tableau public : HTTPS. Administration de lab-vm : SSH. Fichier vers lab-vm : SFTP ou scp selon l’environnement autorisé.
```

### Production

Sélectionne un canal pour chaque opération et explique deux garanties et une limite.

Mode : Production et observation humaine

### Critères proposés

- Table contexte/protocole/justification
- distinction LAN-WAN-VPN
- absence d’identifiants dans la remise

### Transfert individuel

Un site HTTPS demande un mot de passe par message. Le cadenas du navigateur suffit-il à lui faire confiance ?

### Jeu d’amorce — questions et correction professeur

Administrer le terminal d’une VM autorisée ?

Attendu : SSH

SSH fournit un canal distant ; DNS résout un nom, il ne donne pas une session terminal.

Quel élément décrit surtout un périmètre de réseau ?

Attendu : LAN

Le mot LAN ne définit pas une méthode d’authentification ou un format HTTP.

### Notions du socle (texte source, ligne 17)

> protocoles d'échanges : HTTP vs HTTPS, FTP, SSH  
> comprendre les protocoles réseau LAN/WAN/VPN
> expliquer le choix d'un protocole selon le contexte d'usage

## BC01-C2-4 — Expliquer les fondamentaux réseau et les mobiliser pour diagnostiquer un problème de communication simple

### RELAY 2 // La panne entre les couches

**Typologie et niveau source :** Savoir · Non précisé

**Outils source :** Terminal

### Situation d’entrée

Le poste atteint 192.0.2.10 dans les relevés simulés, mais le nom nexus.test échoue. Répare ton raisonnement avant de toucher au pare-feu.

### Cours d’introduction proposé

Une adresse IP identifie une interface sur un réseau ; un port aide à désigner un service de transport. DNS associe des noms à des informations, notamment des adresses. Un switch relaie principalement des trames dans un réseau local ; un routeur relie des réseaux IP.

Le modèle OSI distingue sept couches pour raisonner sur la communication : physique, liaison, réseau, transport, session, présentation, application. L’encapsulation ajoute des informations de protocole autour des données. Ce modèle n’est pas la photographie exacte de chaque pile Internet. ping utilise des messages ICMP : son succès ne prouve pas que le service web répond, et son échec peut venir d’un filtrage. Compare IP, résolution de nom, port attendu et message d’erreur avant de modifier une configuration.

### Exemple

```text
Relevés fictifs : ping IP répond ; nom non résolu ; HTTP non tenté. Hypothèse prioritaire : résolution DNS. Autre cas : nom résolu, connexion TCP refusée → vérifier le service/port.
```

### Production

Associe chaque symptôme à un prochain test et construis un mini schéma routeur-switch-postes.

Mode : Production et observation humaine

### Critères proposés

- Journal observation/hypothèse/test/résultat
- schéma réseau
- limite de ping explicitée

### Transfert individuel

ping ne répond pas, mais la page HTTPS s’ouvre. Comment expliquer ces deux observations sans contradiction ?

### Jeu d’amorce — questions et correction professeur

IP joignable, nom non résolu : prochain contrôle ?

Attendu : Résolution DNS

Les observations isolent un problème de nom sans prouver une panne générale du réseau.

ping répond : peut-on conclure que le site marche ?

Attendu : Non, tester aussi le service web

La disponibilité ICMP et le fonctionnement HTTP sont différents.

### Notions du socle (texte source, ligne 18)

> IP / ports / DNS / Requêtes  
> Architecture des réseaux (Routeur, Switch, appareils) 
> La commande ping
> Encapsulation des données au travers de protocole (model OSI)

## BC01-C3-1 — Décrire les phases du cycle de vie d'un produit numérique

### RELEASE 2 // Un produit n’est jamais fini

**Typologie et niveau source :** Savoir · Non précisé

**Outils source :** Non précisés

### Situation d’entrée

NEXUS veut livrer une alerte sans brief ni recette. Réorganise la production et découvre l’incident qui arrive après la mise en ligne.

### Cours d’introduction proposé

Un produit numérique répond à un besoin et évolue avec ses utilisateurs. Le brief clarifie contexte, problème et contraintes. La conception précise parcours, fonctionnalités et interface. Le développement construit une solution ; les tests et la recette la confrontent aux attentes. Le déploiement la rend disponible dans un environnement cible. La maintenance corrige les problèmes et prépare les évolutions.

Ces phases ne forment pas toujours une ligne à sens unique : un test ou un retour utilisateur peut ramener à la conception. Chaque phase produit des livrables vérifiables : compte rendu, spécifications, maquette, code, rapport de tests, procédure de déploiement, ticket d’incident. « C’est codé » ne signifie ni « c’est conforme » ni « c’est disponible ».

### Exemple

```text
Besoin : prévenir d’une panne. Livrables : scénario d’alerte, maquette, composant, tests d’erreur/succès, procédure de livraison, retour des opérateurs.
```

### Production

Remets les phases en ordre pour une première livraison et ajoute un retour arrière justifié après un test.

Mode : Production et observation humaine

### Critères proposés

- Cycle annoté
- livrable par phase
- évolution post-livraison proposée

### Transfert individuel

Après déploiement, les habitants ne comprennent pas le message. Quelle boucle de travail ouvres-tu ?

### Jeu d’amorce — questions et correction professeur

Le code fonctionne sur le poste du développeur. Que reste-t-il ?

Attendu : Vérifier les attentes et préparer le déploiement

L’exécution locale ne remplace pas la recette ni l’installation dans l’environnement cible.

Une amélioration issue des utilisateurs appartient à…

Attendu : L’évolution du produit

Un produit se maintient et s’adapte après sa première version.

### Notions du socle (texte source, ligne 19)

> Connaître les grandes étapes de production d'un produit web  : brief / analyse du besoin -> conception (fonctionnelle et graphique) -> dev -> tests et recette -> déploiement -> maintenance et évolution
> Identifier les livrables associés
> Comprendre qu'un produit numérique évolue dans le temps

## BC01-C3-2 — Positionner le rôle du développeur au sein d'une équipe projet

### CREW 2 // Former la bonne équipe

**Typologie et niveau source :** Savoir · Non précisé

**Outils source :** Non précisés

### Situation d’entrée

Le bouton d’alerte est ambigu, la route répond 500 et la livraison est bloquée. Distribue les échanges utiles sans supposer qu’un métier travaille seul.

### Cours d’introduction proposé

Les métiers se distinguent par leurs responsabilités, mais collaborent. Le product manager aide à définir la valeur et les priorités ; le chef de projet coordonne l’organisation selon le contexte. Les designers travaillent l’expérience et l’interface. Les développeurs transforment les besoins en logiciel. QA et testeurs contribuent à vérifier la qualité ; DevOps et exploitation participent à rendre les livraisons et les services fiables.

Le développeur ne reçoit pas seulement des ordres en fin de conception. Il pose des questions, signale des risques, propose des alternatives, écrit et teste, documente et participe à la maintenance. Un incident utilisateur peut mobiliser plusieurs personnes : décrire les faits, l’impact et la question à résoudre aide davantage que chercher immédiatement un coupable.

### Exemple

```text
Message utile : « Sur mobile, 3 testeurs sur 4 n’identifient pas le bouton d’alerte. Peut-on revoir son libellé avec le design et vérifier la correction en recette ? »
```

### Production

Relie chaque problème aux interlocuteurs utiles puis prépare une demande de collaboration factuelle.

Mode : Production et observation humaine

### Critères proposés

- Rôles explicités
- message décrivant fait/impact/demande
- responsabilité propre du développeur

### Transfert individuel

Dans une petite équipe, une personne cumule trois rôles. Faut-il supprimer ces responsabilités du schéma ?

### Jeu d’amorce — questions et correction professeur

Un parcours est incompris : qui associer au développeur ?

Attendu : Design et produit, puis vérification avec des utilisateurs

Les rôles peuvent se recouvrir ; le problème doit guider la collaboration.

Que transmettre en signalant une erreur ?

Attendu : Étapes, résultat observé et impact

Des faits reproductibles permettent à l’équipe d’agir.

### Notions du socle (texte source, ligne 20)

> Identifier les principaux métiers intervenant dans un projet numérique : développeur, designer, product manager, chef de projet, DevOps, testeur, QA
> Comprendre les interactions entre les différents métiers : collaboration, communication, rôle de chacun dans un projet
> Se positionner en tant que développeur au sein d'une équipe en identifiant les interactions avec les autres métiers du numérique.
