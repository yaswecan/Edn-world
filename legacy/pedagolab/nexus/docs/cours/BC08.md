## BC08-C1-1 — Modéliser un modèle logique (MCD et MLD)

### MEMORY MAP // Modéliser avant de stocker

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** Merise

### Situation d’entrée

Les alertes contiennent le nom complet du secteur copié partout. Un changement produit dix versions différentes. Modélise les données à partir du besoin.

### Cours d’introduction proposé

Le modèle conceptuel décrit entités, attributs et associations du métier. Les cardinalités expriment combien d’occurrences peuvent ou doivent être reliées. Un dictionnaire précise sens, type attendu et contraintes des données. Le modèle logique traduit ces relations en structures adaptées, notamment tables, clés primaires et clés étrangères pour le relationnel.

Une clé identifie une occurrence de façon stable ; un nom susceptible de changer n’est pas toujours un bon identifiant. Distingue donnée à conserver et valeur calculable. Vérifie le cycle de vie : création, modification, suppression et conservation. Le schéma doit répondre aux questions du cahier des charges et éviter les redondances incohérentes.

### Exemple

```text
Secteur(id, nom) ; Alerte(id, secteur_id, message). Un secteur possède 0..n alertes ; une alerte appartient à un secteur dans ce scénario.
```

### Production

Produis dictionnaire, MCD puis MLD du système d’alertes, en justifiant les cardinalités.

Mode : Production et observation humaine

### Critères proposés

- Modèles liés au CDC
- clés stables
- cardinalités
- règles de qualité et de cycle de vie

### Transfert individuel

Une alerte peut désormais concerner plusieurs secteurs. Quelle association et quelle table deviennent nécessaires ?

### Jeu d’amorce — questions et correction professeur

La cardinalité décrit…

Attendu : Le nombre possible ou obligatoire de relations

Elle traduit une règle métier, pas une préférence graphique.

Pourquoi éviter de copier le nom du secteur dans chaque alerte ?

Attendu : Pour limiter les incohérences de mise à jour

La modélisation centralise les faits qui doivent rester cohérents.

### Notions du socle (texte source, ligne 178)

Identifier les données à informatiser (dictionnaire des données)
Structurer les données en tables/entités, définir les clés primaires
Définir les relations et cardinalités
Savoir créer un MLD à partir du MCD
information métier

qualité des données

## BC08-C1-2 — Modéliser le modèle physique (avec jointures) + UML

### SCHEMA FORGE // Du modèle aux tables

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** MySQL

### Situation d’entrée

Le MLD est juste, mais le schéma physique n’applique aucune clé étrangère. Traduis les relations dans MySQL et relie-les au diagramme UML.

### Cours d’introduction proposé

Le modèle physique précise les tables, colonnes, types, clés, contraintes et index pour un système donné. Il met en œuvre le modèle logique sans perdre les règles métier. Les relations d’un schéma Merise et celles d’un diagramme UML s’expriment différemment mais doivent représenter le même besoin.

Une jointure relie des résultats selon des clés ; elle n’est pas une clé étrangère. La contrainte protège la cohérence des données, tandis que JOIN organise une lecture. Vérifie les types compatibles et les actions prévues en cas de suppression. Teste un enregistrement valide puis une référence inexistante pour observer le rôle de la contrainte.

### Exemple

```text
CREATE TABLE secteurs(id INT PRIMARY KEY, nom VARCHAR(80) NOT NULL);
CREATE TABLE alertes(id INT PRIMARY KEY, secteur_id INT NOT NULL, FOREIGN KEY (secteur_id) REFERENCES secteurs(id));
```

### Production

Traduis le MLD en SQL MySQL, dessine l’équivalent UML simplifié et exécute une jointure de lecture.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- DDL réel
- clés et contraintes
- diagramme cohérent
- insertion invalide refusée

### Transfert individuel

Le métier autorise la suppression d’un secteur uniquement sans alerte active. Où formalises-tu cette règle ?

### Jeu d’amorce — questions et correction professeur

Une jointure et une clé étrangère sont…

Attendu : Une opération de lecture et une contrainte distinctes

Lire les relations et contraindre les écritures sont deux fonctions.

Le modèle physique doit conserver…

Attendu : Les règles et relations du modèle logique

La traduction ne doit pas perdre les contraintes métier.

### Notions du socle (texte source, ligne 179)

Création de la BDD à partir d'un MLD
Modélisation avec Merise ET UML à partir de spécifications détaillées

## BC08-C2-1 — Créer une base de données

### DATABASE SHELTER // Créer et pouvoir restaurer

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** MySQL

### Situation d’entrée

La base de test fonctionne avec le compte administrateur partout et aucune sauvegarde. Prépare une structure et un accès de laboratoire maîtrisés.

### Cours d’introduction proposé

Créer une base demande tables, types, clés et contraintes appropriés aux données. Les clés primaires identifient les lignes ; les clés étrangères contribuent à l’intégrité référentielle. NOT NULL, valeurs uniques et contraintes utiles traduisent certaines règles.

L’administration inclut aussi utilisateurs, droits, sauvegarde et restauration. Dans phpMyAdmin ou le client autorisé, attribue à l’application uniquement les droits nécessaires. Une sauvegarde dont la restauration n’a jamais été testée reste une hypothèse de récupération. Travaille dans une base jetable nommée explicitement, sans modifier les comptes ni les bases du serveur PédagoLab.

### Exemple

```text
Base de TP séparée : nexus_labo. Compte de lecture pour un tableau de bord ; compte d’application pour ses seules opérations prévues. Export puis restauration dans une autre base de TP.
```

### Production

Crée la base MySQL du TP, un utilisateur limité et une sauvegarde que tu restaures sous un autre nom.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Tables/contraintes
- droits vérifiés
- sauvegarde et restauration réelles
- secret absent du rendu

### Transfert individuel

L’application a seulement besoin de lire les alertes. Quels droits ne faut-il pas lui attribuer ?

### Jeu d’amorce — questions et correction professeur

La restauration teste réellement l’usage de la sauvegarde.

Attendu : Les droits nécessaires à ses opérations

Limiter les droits réduit les conséquences d’une erreur ou faille.

## BC08-C3-1 — Écrire des requêtes CRUD

### SQL RECOVERY // Modifier la bonne ligne

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** SQL

### Situation d’entrée

Une commande UPDATE sans filtre menace toutes les alertes du laboratoire. Prévisualise le périmètre avant d’écrire.

### Cours d’introduction proposé

SQL permet de lire avec SELECT, créer avec INSERT, modifier avec UPDATE et supprimer avec DELETE. Le traitement doit découler de la règle métier : quelles lignes, quelles colonnes et quel résultat. WHERE limite les lignes concernées ; son absence peut étendre une modification à toute la table.

Avant une écriture, vérifie le périmètre avec une lecture équivalente et travaille sur des données de TP réinitialisables. Une transaction permet de regrouper des opérations selon le moteur et le contexte, avec validation ou annulation. Relis ensuite le résultat et vérifie qu’aucune ligne non ciblée n’a changé. Un affichage vide n’indique pas toujours une base vide : le filtre peut être faux.

### Exemple

```text
SELECT id, statut FROM alertes WHERE id = 42;
UPDATE alertes SET statut = 'resolue' WHERE id = 42;
SELECT id, statut FROM alertes WHERE id = 42;
```

### Production

Sur la base de TP, exécute un CRUD complet, vérifie les lignes concernées et démontre une annulation contrôlée.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Quatre requêtes réelles
- filtres justifiés
- état avant/après
- absence de modification hors périmètre

### Transfert individuel

La consigne dit « toutes les alertes résolues du secteur nord ». Quelles conditions faut-il combiner ?

### Jeu d’amorce — questions et correction professeur

Avant un UPDATE sensible, une bonne observation est…

Attendu : Un SELECT avec le même périmètre

Prévisualiser les lignes réduit les erreurs de ciblage.

UPDATE sans WHERE peut…

Attendu : Modifier toutes les lignes de la table

Le périmètre doit être explicite et vérifié.

### Notions du socle (texte source, ligne 181)

SELECT / INSERT / UPDATE / DELETE

## BC08-C3-2 — Requêtes avancées et objets SQL

### JOIN CITY // Voir aussi les absents

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** SQL / MySQL

### Situation d’entrée

Le rapport oublie les secteurs sans alerte. Change la jointure puis examine vues, procédures et triggers sans déplacer les règles au hasard.

### Cours d’introduction proposé

INNER JOIN conserve les correspondances ; LEFT JOIN conserve toutes les lignes de gauche et met des valeurs NULL lorsqu’il n’y a pas de correspondance à droite. Le placement d’un filtre peut annuler l’effet recherché d’une jointure externe.

Une vue nomme une requête ; une procédure stockée regroupe des instructions appelables ; un trigger réagit à un événement sur une table. Ces objets peuvent aider mais rendent aussi des effets moins visibles s’ils sont mal documentés. Les fonctions de dates et chaînes, filtres, tris et regroupements complètent les lectures. Vérifie les résultats sur un jeu contenant correspondance, absence et plusieurs relations ; documente tout effet d’écriture.

### Exemple

```text
SELECT s.nom, a.id FROM secteurs s LEFT JOIN alertes a ON a.secteur_id = s.id;
-- Inclut un secteur sans alerte, avec a.id NULL.
```

### Production

Construis les deux jointures, une vue, une procédure et un trigger simples dans MySQL de TP ; compare leurs rôles et effets.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Résultats sur données de contraste

- date/chaîne/tri utilisés
- effets documentés

### Transfert individuel

## BC08-C4-1 — Utiliser une base dans une application via PDO

### PDO BRIDGE // Les données ne sont pas du SQL

**Typologie et niveau source :** Savoir-faire technique · A2

**Outils source :** PHP / PDO

### Situation d’entrée

L’API assemble une requête en collant le texte reçu. Sépare la valeur et l’instruction avec PDO.

### Cours d’introduction proposé

PDO fournit une interface PHP pour accéder à différentes bases via leurs pilotes. La connexion utilise un DSN, un utilisateur et une configuration. Les secrets restent hors du code publié. Une requête préparée décrit les instructions ; les paramètres transmettent les valeurs séparément à l’exécution.

Un paramètre ne remplace pas librement un nom de table ou de colonne : ces choix demandent une liste autorisée si le besoin les rend variables. PDO n’est pas un ORM ; un ORM propose une abstraction supplémentaire autour des objets et de la persistance. Traite les erreurs sans exposer les accès et vérifie les données réellement lues ou écrites.

### Exemple

```text
$stmt = $pdo->prepare("SELECT id, statut FROM alertes WHERE id = :id");
$stmt->execute(["id" => $id]);
$alerte = $stmt->fetch(PDO::FETCH_ASSOC);
```

### Production

Connecte le TP PHP à MySQL, remplace une concaténation par des paramètres et vérifie lecture, absence et erreur.

Mode : TP réel dans l’outil indiqué, hors sandbox

### Critères proposés

- Connexion réelle
- paramètres préparés
- secret non livré
- résultat contrôlé
- PDO/ORM distingués

### Transfert individuel
